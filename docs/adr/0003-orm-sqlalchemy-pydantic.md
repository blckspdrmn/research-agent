# ADR-0003: DBモデルとAPIスキーマを分離する(SQLModelを採用しない)

- 日付: 2026-08-10
- ステータス: 採用(Accepted)

## 背景・課題
DBのテーブル定義(SQLAlchemy)とAPIの入出力定義(Pydantic)を、統合するか分離するかを決める必要がある。分離すると `title` や `description` を2箇所に書くことになり、一見すると二重管理に見える。

FastAPIの作者が開発している **SQLModel** を使えば、この2つを1つのクラスに統合でき、フィールドの記述は1回で済む。

## 選択肢
1. SQLModel(SQLAlchemyとPydanticを統合)
2. SQLAlchemy + Pydantic を分離して併用

## 決定
分離して併用する。`models.py`(SQLAlchemy)と `schemas.py`(Pydantic)を別ファイルとして持ち、`schemas.py` 側に `from_attributes = True` を指定して変換する。

## 理由
- **2つは異なる契約を表しており、一致しないことに意味がある**
  - `models.py` はDBに対する定義
  - `schemas.py` は**APIの利用者に対する約束**
- **DBには保存するが外部に出さない列が必ず出てくる**(`user_id`、認証導入時に追加する外部IDなど)。分離していれば、モデルに列を追加してもAPIの出力は自動では増えない。面倒に見えるが、**内部の列がうっかり外部に漏れない**という安全側の設計になる
- 逆に「一覧にレポート件数を含めたい」のように、**APIには出したいがDBの列ではない**ものも表現できる
- 入力用スキーマを分けること自体が **Mass Assignment脆弱性** への防御になる。`ThemeCreate` に `user_id` が無いため、リクエストボディで所有者を偽装できない
- SQLModelは比較的新しく情報量が少なめで、詰まった際は結局SQLAlchemy本体のドキュメントを読むことになりやすい。素のSQLAlchemyはAlembicとの相性も含めて実績が厚い

## 結果・影響
- 1テーブルに対しスキーマが複数並ぶ(`ThemeCreate` / `ThemeUpdate` / `ThemeOut`)。それぞれ「作成時にクライアントが決めてよい項目」「更新してよい項目」「外部に見せてよい項目」という異なる契約を表す
- **モデルに列を追加してもAPIの出力は自動では増えない**。「DBには入っているのにレスポンスに出てこない」場合は、まず出力スキーマ側に定義したかを確認する
- クラス名の衝突を避けるため、レスポンス用スキーマには `〜Out` の接尾辞を付ける
