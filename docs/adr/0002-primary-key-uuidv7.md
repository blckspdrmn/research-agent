# ADR-0002: 主キーにUUIDv7を採用

- 日付: 2026-08-09
- ステータス: 採用(Accepted)

## 背景・課題
`users` / `themes` / `reports` の主キーの型を決める必要がある。主キーの型は一度決めると、テーブル・マイグレーション・APIの型定義・フロントエンドの型まで波及するため、後から変更するコストが非常に高い。

## 選択肢
1. 連番の整数(`SERIAL` / `IDENTITY`)
2. UUIDv4
3. UUIDv7

## 決定
UUIDv7を採用する。採番はアプリ側ではなくDB側に任せ、PostgreSQL 18の組み込み関数 `uuidv7()` を `server_default` に指定する。

## 理由
- **IDを推測できないようにする**: 連番だと `/themes/1`、`/themes/2` と順に叩くだけで他人のデータの存在を総当たりで確認できてしまう
- **採番を単一のシーケンスに依存させない**: 連番の整数はDB内の1つのシーケンスオブジェクトが番号を発行するため、採番が1箇所に集中する。UUIDは生成側がそれぞれ独立に採番できるので、将来ジョブワーカーを複数台に増やしたりテーブルを分割したりしても、IDの衝突を考慮せずに済む
- **v4ではなくv7を選ぶ理由**: UUIDv4は完全なランダムのため主キーのB-treeインデックスの挿入位置が毎回分散し、行数が増えるほど書き込みが遅くなる。UUIDv7は先頭にミリ秒精度のタイムスタンプを持ち生成順に値が増えるため、挿入がインデックスの末尾に集中する。連番整数に近い書き込み特性を保ちながら推測不可能性を得られる

## 結果・影響
- **PostgreSQL 18以上が前提条件になる**。`uuidv7()` は18で追加された組み込み関数(Python標準ライブラリに `uuid7()` が入るのは3.14からで、本プロジェクトの3.12にはない)
- IDが推測できないことは防御の本体ではない。**取得系のクエリを必ずユーザーで絞る**ことが本命の対策であり、UUIDはそれを補強する一枚にすぎない
- 動作確認でIDのコピー&ペーストが必要になり、目視でのIDの識別が難しくなる
- 主キーは全ての外部キーから参照されるため、**文字列型(36文字)ではなく `uuid` 型(16バイト固定長)で保存する**こと。文字列で保存すると容量が2倍以上になり、インデックスも肥大化する
